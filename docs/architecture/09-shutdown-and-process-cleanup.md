# 9. Shutdown & Process Cleanup

This chapter distinguishes window close (shared daemon retained), manual Restart (owned work stopped, then re-exec) and Panic (explicit stop). Each defines signals, unconfirmed custody and next-generation reconciliation, so no uncertain stop becomes a false receipt.

Ordinary window close preserves this installation's shared Claudexor daemon and other clients' work on both graceful and forced cleanup. It stops the server generation's workers/services, waits for its group or Job, cleans owned processes and releases the PID lock. The Windows daemon stays outside the launcher Job; old immutable launchers need a package update for this guarantee.

`launcher.stop_agent` sends `proc.terminate()` ONLY to the server PID on all platforms, waits `LAUNCHER_STOP_GRACE_SEC`, then retains the group SIGKILL fallback/post-exit sweep. The server owns its multiprocessing Manager and pool: group SIGTERM at t=0 killed them before teardown, causing three `EVENT_Q` BrokenPipe errors and a false `supervisor_failure` alarm (#1142). Against old launchers, `server_process._SignalStopServer.handle_exit` sets `_supervisor_stop` at the signal; torn-Manager errors are not crashes. `uvicorn.Config(timeout_graceful_shutdown=SERVER_GRACEFUL_SHUTDOWN_TIMEOUT_SEC)` bounds HTTP/WS drain within the launcher budget (paired in `runtime_limits.py`). Embedded Host Service's `_embedded_uvicorn_server` uses instance `capture_signals=nullcontext`, avoiding uvicorn taking process handlers until its own drain. The never-cleared `_exit_signalled` latch refuses `_start_supervisor_if_needed`, ends a just-admitted `_supervisor_generation`, and fences loop/crash paths, so mid-teardown settings cannot revive work behind `kill_workers`. §5's `_supervisor_stop` remains revivable for crash recovery/fresh lifespan; `tests/test_shutdown_signal_1142.py` exercises old group SIGTERM with an open request.

Same-pin planned restart retains the daemon. Changed-pin restart compares landed `load_runtime_pin` with attach-only `read_owned_gateway`, then stops via `_stop_owned_daemon_for_new_pin`. Unpublished/unreadable pins and unreachable/foreign/stopped daemons leave handoff unchanged. Unconfirmed stop preserves custody/diagnostics while restart proceeds; the next generation reconciles without invented spend.

Lifespan teardown prioritizes the irreversible durable interruption write: stop flag, bounded supervisor join, then `kill_workers` terminalization, before best-effort extension reconciliation, Host Service waits and kill-all sweeps. This keeps persistence reachable within the launcher force-exit budget; SIGKILL can still cut it short and bridge/event-bus teardown can lose late frames. If it misses that write, next-generation snapshot restore owns recovery. Queue init hands over `state/direct_roots.json` before clearing it, fencing listed roots like surviving RUNNING rows: Cancelled, not infra-failed orphans. Ordinary shutdown closes its own Host Service listener. Reserved-port sweeps remain separate launcher/recovery/Panic behaviour; they do not prove PID identity and may stop unrelated listeners.

Manual Restart (`/restart`, chat Restart) uses `server_restart._perform_owner_restart` (re-exported by `server`) with the transport notice callback. HTTP binds the same Restart/Panic operations before bridge publication; deferred execution requires a live supervisor and published bridge, otherwise the direct owner executes. `_safe_restart_serialized` takes the update lock, checks the managed-update transaction, then runs `safe_restart` checkout/dependency/import/stable-fallback work BEFORE stopping anything. Any refusal, including an unwritable no-resume flag, answers “Restart cancelled” and leaves the server intact.

After that boundary, Restart proceeds despite unconfirmed cleanup: persist `owner_restart_no_resume.flag` plus compatibility `panic_stop.flag`; `_stop_owned_work` requests `owner_restart` cancellation for RUNNING/direct/post-task work except SAVED pauses; run `kill_workers(hold_never_started=True)`, `reconcile_orphaned_runs(running_task_ids=set())` through attach-only `read_owned_gateway`, then the attested daemon `stop_outcome()` used by Panic. No `ensure_owned_gateway` may wake a stopped daemon. Worker failure logs critically; daemon uncertainty emits `process_stop_unconfirmed`; neither erases custody nor vetoes restart. This stop is installation-wide, including another client's daemon runs, unlike ordinary window close.

Boot keeps `owner_restart` in `delegate_recovery.NO_RESUME_CAUSES`: no adoption. Startup reconciles owner-gone runs: absent → `close_absent_run` without invented spend; journal terminal → settlement; pending invocation → its original key. Model `dispatched`/`unresolved` rows retain their monetary upper bound. After an unconfirmed stop, attach to the surviving daemon instead of spawning a duplicate; provisioned homes retain the lifespan's background `warm_owned_daemon()`. Planned restart, update handoff and Panic keep their separate contracts.

**Retention (owner Batch4 7A).** `supervisor/restart_retention.py` is shared by the Restart cancel census, RUNNING/PENDING teardown, restore and boot-marker consumption. Every stop preserves a saved live-attempt pause, including checkpoint-written/park-event-pending RUNNING and direct actors: after workers are signalled, park under the exact marker, without terminalization or `task_done`. Revoke unused Resume grants back to their pause. Warm-sleep conversion, including failed markerless retention, carries the actual Restart/Panic hold; kill and restore upgrade a generic recovery hold so the Restart count stays accurate. Explicit Stop outranks it; `pausing` without a source is interrupted intent eligible only for Continue, never exact Resume.

Manual Restart additionally retains positive `admitted_dispatch=none` queue rows, including children of interrupted parents, under `_budget_pause_hold`/`reason_code=owner_restart_hold`. Historical `paused_before_dispatch` rows keep their original pause and Resume without becoming “never started.” Missing dispatch evidence keeps the same row under `dispatch_outcome_unknown`; ordinary Resume refuses it and no `none` is invented. Known `possible` rows keep interruption policy; restore holds unresolved handoffs. Zero model rounds and terminality prove no dispatch outcome. Batch1 still owns scheduled-occurrence receipts. Subsequent teardown/restore retains held rows at any age. Only explicit owner Resume or model selection under a live root grant releases selectable holds; Stop cancels. No policy is inferred for other doors, and Panic gets no prerequisite: retention reads follow signalling. The Restart notice reports the held count.

Panic is a complete explicit owner stop, not a restart: stop consciousness, record evolution owner-stop state, close the campaign and pending promotion, write `panic_stop.flag`, stop local models and call `OwnedClaudexorDaemon.stop_outcome` before worker cleanup, then end tracked foreground commands, executor processes, services, companions and workers before hard server exit. The shared daemon may belong to a previous generation and is outside the Windows launcher Job, so its explicit stop, not closing that Job, owns termination; a failure emits a critical `process_stop_unconfirmed` row and retains unresolved custody while the rest of Panic continues. The next launch suppresses automatic work under the panic/no-resume flags.

`stop_outcome` returns `stopped`, `nothing_to_stop` or disclosed `unconfirmed`. With a valid owned marker and an authenticated same-home endpoint it first invokes the installed managed CLI `daemon stop --json` (read-only `resolve_cli_command(require_npm=False)`: operator shutdown needs the existing exact Node, not the npm installation toolchain); it never ensures a runtime, wakes a daemon or probes accounts. Exit 0 plus the typed terminal CLI receipt is required — an RPC acknowledgement or a clean lease release does not prove the captured OS processes have exited — and a surviving authenticated endpoint is disclosed without chasing a successor. The pre-request custody snapshot limits forced fallback to those original rows, and forced signalling still requires both measured birth and command identity or the manager's own Popen; legacy Windows empty-birth rows cannot authorize signals, though a healthy attached daemon can still stop cooperatively through the CLI. Token refusal, invalid discovery, malformed responses and a matching error-code string alone never provide stop authority. Only confirmed death permits signal-stop custody removal; concurrent rows survive.

The short manager lock retires the local startup generation before waits and never spans runtime preparation, network or process-exit work. CLI RPC, termination confirmation and startup slack use `config.CLAUDEXOR_OPERATOR_STOP_TIMEOUT_SEC`; captured-process observation uses `config.CLAUDEXOR_STOP_EXIT_WAIT_SEC` (both owned by `runtime_limits`); the phases promise no absolute total stop duration. A live startup outlives its caller's window (20 seconds by default, independently narrowable): `daemon_starting` invites joining the same work, whereas `daemon_spawn_failed` identifies the exited child/build/log interval. Native Windows Job/identity/stop behaviour and frozen psutil imports require Windows/package evidence; portable fixture success does not establish that proof.

**Startup failure: typed classification, one durable row, the spawn latch.** When this manager's own child exits without a control endpoint, `claudexor_startup_failure.py` classifies the failure from the child's own identity-checked `daemon.log` interval into `heap_exhausted` (V8's fatal heap-limit banner), `writer_lease_contended` (the engine's single-writer refusal), `engine_floor` (the root-authority version-floor refusal) or `unclassified`. The classification is diagnostic only — it names the failure in the typed `daemon_spawn_failed` detail, in `last_error` and in one durable `claudexor_daemon_start_failed` supervisor row (pin, exit code or signal, descriptor written or not, classification, log interval, `latched`, `ts`) — and never selects behaviour. The latch keys on the typed exit fact alone: the child exited by signal or non-zero and wrote no control descriptor during that spawn; a clean exit or a crash after publishing control is rowed with `latched=false`, and a joined peer startup that vanished is not rowed. While latched, every ordinary caller (delegation, model calls, review, warmup) receives the same immediate `daemon_spawn_failed` refusal, before runtime preparation and without a new spawn — unless a live startup exists, which it joins, because refusing there would hide a daemon that may come up. Releases — three are rowed as `claudexor_daemon_start_latch_cleared`, the fourth is not: attaching to a live authenticated daemon (`cleared_by=live_daemon_attached`); the ~600 s periodic supervisor sweep (`cleared_by=supervisor_sweep`), itself off the loop thread and attach-only once a stop is in flight, which only when it actually released a latch makes exactly one zero-wait ensure on a short-lived background thread, so a healthy install never spawns or waits in the sweep and a persistently crashing engine costs one spawn per period; the owner's explicit Refresh (`/api/claudexor/wake`, `cleared_by=owner_wake`), one spawn per press; and the owner's Restart or Panic, which release it without a row by constructing a new manager. The latch is per-manager state and the manager is a process global: the sweep and the Refresh release the server process's latch, while a task worker holds its own, released only by a live-daemon attach or the worker's respawn. There is no backoff, counter, cooldown, heap policy or new timing constant: the host neither derives the engine's heap from host RAM (V8's default old space is 4096 MiB on any machine with ≥ 8 GiB, so a guessed size only moves the crash, and the engine's bounded replay removes the need) nor touches the writer lease. `NODE_OPTIONS` set on the server process is inherited by the spawned daemon unchanged — the operator's documented escape hatch (for example `NODE_OPTIONS=--max-old-space-size=8192`), not a product mechanism. The registration pass of the same sweep (`retire_settled_registrations`) reaches the daemon only for a registration every sharer has settled. A DELETE refused with the typed code `project_has_threads` is discharged once as `PROJECT_RETIRED {project_kept: true, reason, code, status}`; any other failure leaves a retryable `PROJECT_RETIRE_FAILED` row with the typed code and status. The harvest cadence and the two disclosed residuals are stated once, in DEVELOPMENT's Process Custody Rule.

Bounded foreground `run_command`/`run_script` processes ride the in-memory `_active_subprocesses` panic registry; long-lived children — services, executor-backed processes, extension companions, delegated runtimes — enter durable exact-identity process custody via `spawn_supervised` (§1 Runtime topology). Unix process groups and Windows Job Objects provide tree cleanup; durable executor and service records let the host recover after worker death. Normal cleanup may archive logs, while panic skips nonessential finalization — agent-controlled or wedged cleanup must not delay an owner stop. Timeout and signal exits remain distinct in tool results so a killed command never resembles success.


**G1 future work controls.** The full stated cancellation reason is retained. Recorded cancel intent wins; a proven absent intent uses the actual shutdown door's cause, while an unreadable store must not invent one. An accepted explicit Stop also transfers its exact future-work control identity to the original task result before active intent retirement, including when natural completion wins. That transfer preserves the completed status, result and custody. A failed transfer keeps the active intent for recovery. Manual Restart retains a schedule control in the existing schedule document before consuming its marker; Panic gains no prerequisite. These schedule control identities do not make the legacy global flag carriers generation-aware; that Batch1 integration remains parent-owned.
